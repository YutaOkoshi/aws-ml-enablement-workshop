## 冷蔵庫の残り食材から献立を提案する機能 : ○○社 XX レシピアプリより

* いつ使う? : 帰宅途中の電車内や、スーパーに入る直前に「今日は何を作るか」を決めるとき
* どう課題を解決した? : 献立を決められない原因は、レシピの数が足りないことではなく「家に何が残っているか分からず、買い物と献立を同時に考えなければならない」ことにあった。冷蔵庫の中身をスマホで撮影すると食材を認識し、残っている食材を優先して使う献立を 3 案提示する。足りない食材だけを買い物リストに出す
* どんな効果が出た? : 献立決定までの時間が平均 15 分から 3 分に短縮、食材の廃棄量が 30% 減少
* どう実現している? : 画像認識による食材の識別、在庫と賞味期限の推定、レシピデータベースとのマッチングを組み合わせている

参考 : https://example.com/solution-1

## 調理時間を基準にした献立の並べ替え : △△社 □□ 献立サービスより

* いつ使う? : 帰宅後すぐに料理を始めたい平日の夕方
* どう課題を解決した? : 一般的なレシピサイトの所要時間は「手際の良い人が 1 品を作る時間」で、主菜と副菜を並行して作る実際の時間と合わない。そのため 30 分で終わる予定が 1 時間かかり、平日に使われなくなっていた。主菜・副菜・汁物を同時に作る前提で工程を並べ直し、コンロや電子レンジの同時使用を考慮した実時間を表示する。表示時間内に終わる組み合わせだけを提案する
* どんな効果が出た? : 平日の利用率が 2.1 倍に増加、「表示どおりの時間で作れた」と答えた利用者が 78%
* どう実現している? : レシピの工程分解、調理器具の利用状況を制約にした工程スケジューリングを組み合わせている

参考 : https://example.com/solution-2

## 子どもの好き嫌いを学習する献立調整 : ××社 ◇◇ 家族向けアプリより

* いつ使う? : 幼児・小学生がいる家庭で、週末に翌週の献立を考えるとき
* どう課題を解決した? : 子どもが食べ残すと作り直しや追加の 1 品が必要になり、結局同じ献立ばかりになって栄養が偏る。食後に「完食 / 少し残した / 食べなかった」を 1 タップで記録すると、子どもが食べやすい味付け・切り方・食材の組み合わせを学習し、苦手な食材を食べやすい形で取り入れた献立を提案する
* どんな効果が出た? : 子どもの完食率が 55% から 72% に向上、1 週間に使う食材の種類が平均 1.4 倍に増加
* どう実現している? : 家族ごとの嗜好プロファイル、レシピの特徴量（味付け・食感・切り方）による推薦、栄養素の充足度計算を組み合わせている

参考 : https://example.com/solution-3

* いつ使う? : 昼休みや帰宅途中に、その日の夕方に届く食材を注文するとき
* どう課題を解決した? : 共働き世帯は帰宅後にスーパーへ寄る時間が取れない日がある一方、食材宅配の定期便は献立の自由が利かず解約されやすかった。献立を選ぶと必要な食材が分量つきでネットスーパーのカートに入り、最短当日 18 時以降の配送枠をそのまま予約できる

* どう実現している? : レシピの材料と商品マスタのマッピング、在庫と配送枠の API 連携を組み合わせている

## 難易度の評価基準

難易度は「技術としての難しさ」ではなく **「このチームが実際に手を動かして完成させられるか」** を測る尺度です。ここでの「完成」は、顧客に触ってもらえるものが動き、その反応を計測できる状態を指します。次の 4 段階から選び、その数字にした理由（何が分からないのか、何に時間がかかるのか）を 1 行添えてください。

- **1 : 1 週以内に動くものが出る** — チームが経験済みの技術と既存の基盤・SaaS・API の組み合わせで作れる。詰まりそうな箇所が見当たらない
- **3 : 1 か月以内に完成できる** — 大筋は経験の範囲内だが、一部に未経験の要素がある。調べながら進めれば動くところまで到達できる
- **5 : 四半期規模の仕事になる** — 未経験の技術、あるいはチーム外との調整（データ整備、権限、他部署の協力）が中心を占める。誰が何をやるかを決める段階から始まる
- **10 : 完成までの見通しが立たない** — 今のチーム・データ・体制では道筋が描けない。作れるかどうかを確かめる検証から必要になる

評価は **今のチームの構成と経験** を前提にします。「人を採用できれば」「時間を無制限にかければ」という仮定は置きません。

### 複数の解決策を組み合わせた発明の難易度

1 / 3 / 5 / 10 は順序を表す段階なので、そのまま足し算すると意味を失います（1 が 3 つあっても 3 にはなりません）。組み合わせた発明の難易度は次の手順で求め、**結果は必ず 1 / 3 / 5 / 10 のいずれかにしてください**。

1. **最も難しい構成要素の値を基準にする**。全体が一番難しい部分より簡単になることはありません
2. **統合の手間が大きいときだけ 1 段階上げる**（構成要素が 3 つ以上ある、要素間でデータを受け渡す、画面を一体で作り直す等）。例 : 3 と 3 と 1 の組み合わせ → 基準 3 を 1 段階上げて 5
3. **同じ経験・同じ基盤を使う構成要素は二重に数えない**。同一の音声解析基盤に乗る 2 つの機能は、1 つ分として扱います

## 良い解決策記述のチェックポイント

- **具体的な利用シーン**: 「いつ使う?」で明確な使用タイミングを記述
- **課題の本質理解**: 表面的な課題だけでなく、根本原因まで言及
- **定量的な効果**: 可能な限り、数値で示せる改善効果を含める
- **実現方法の明示**: 技術的なアプローチを開示されている範囲で具体的に説明
